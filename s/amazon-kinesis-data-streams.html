Amazon Kinesis Data Streams

Analytics  ·  Common, learn when you need it

A pipe that holds a stream of events for a while so several programs can read them.

Picture it as

A conveyor belt past several workstations. Each worker reads items as they pass, at their own speed, and the belt keeps them for a day before they fall off the end.

What it actually does

Producers write records, consumers read them independently, and each keeps its own place in the stream. Records stay for 24 hours by default and up to a year if you pay for it, so you can replay. Order is guaranteed only within a shard, not across the whole stream, which is the thing people get wrong. You either manage shard counts yourself, provisioned mode, or let it scale on demand.

Reach for it when

  • Several different systems need the same live event feed
  • You need to replay recent events after fixing a bug
  • Ordering matters per user or per device

Do not reach for it when

  • If you just want events landing in S3, use Amazon Data Firehose, far less work
  • For a work queue where each message is handled once and then deleted, use Amazon SQS
  • If you need Kafka APIs or existing Kafka tooling, use Amazon MSK

One small example

Every card swipe goes into a stream, read at once by the fraud checker, the ledger, and the analytics loader.

How you pay

Provisioned mode bills per shard hour whether data flows or not, plus per record unit. On-demand is simpler but costs several times more per GB, and long retention adds another charge.
